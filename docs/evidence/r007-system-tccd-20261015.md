## Endpoint/domain verification (unfiltered, on-device)

- `launchctl print system/com.apple.tccd.system` → "Could not find
  service" (exit 113). iPadOS **never** registers that name anywhere.
- iOS's own daemon is only `user/501/com.apple.tccd` (uid 501, pid
  23321, `uses proxy`). It is a different service name and stays
  untouched.
- The compatible endpoint is project-owned:
  `com.apple.macosbooter.tccd.system`, declared by
  `layout/usr/macOS/LaunchDaemons/com.macwsguide.tccd-system.plist`
  (`MachServices{…:true}`, `tccd system` via `launchdchrootexec`).
- macosbooter jobs land in the **loading context's** domain (user/501
  when `macos_gui.sh` runs over SSH — the "SSH domain trap" already
  documented for these jobs), not `system/`. `start_tccd_system()`
  therefore searches `system`, `user/501`, `user/0`, `gui/501` service
  tables for the registered endpoint instead of assuming a domain.
- Static fallback re-verified on `analysis/TCC_22F82` (UUID
  `1238D7CA-719A-36A4-94B1-2F387E6B3BF1`): `tccd()` csel's the name on
  `flags` (`com.apple.tccd.system` when flags=1) and the send loop tries
  the user connection then the system connection — observed as
  `w5`=0/1 alternating in R006's pane.

## The mapping fix this round actually needed

`com.apple.tccd.system` → `com.apple.macosbooter.tccd.system` had been
added to `macws_private_bootstrap_service_name()` (`mac_hooks.m`) but the
XPC path is a **second, parallel table**:
`macws_private_chroot_service_name()` in `Metal_hooks.x` — the file's own
comment says the tables must stay identical. Live symptom: other services
logged `'orig' -> 'macosbooter…'` in `XPC_TRACE`, while
`com.apple.tccd.system` showed **no arrow** (trace prints post-map;
`name != originalName` only when translated). Added the identical entry
to `Metal_hooks.x` (only the system-scope name; `com.apple.tccd` remains
unmapped so iOS keeps its user daemon and the stock user→system fallback
ordering is preserved). Both slices rebuilt, macOS-versioned, signed,
fresh-inode installed to both `…/usr/macOS/lib/` and
`…/usr/local/lib/`, trustcache re-added, string verified in all four
deployed files.

## What changed vs. R006 — honest reading

- The transport invariant is repaired end-to-end: the genuine Ventura
  `tccd system` daemon serves the private endpoint, the Ventura client
  lookup is translated, `bootstrap_look_up` succeeds, and a **real reply
  dictionary** makes the round trip (three of three attempts).
- `rc=1002` persists but its producer changed: the daemon's reply now
  carries `result=false` — a genuine TCC policy answer for the caller's
  identity, not the preflight's transport-failure default. The deny is
  produced by real TCC semantics evaluating an adhoc chroot client, which
  is the expected answer for an ungranted PostEvent requester.
- Nothing was bypassed: no hooks on checks, no forced result, no TCC.db
  edits, no grants fabricated. iOS `com.apple.tccd` (uid 501, pid 23321)
  untouched and coexisting.

## Limits (explicit)

- `result=false`'s basis inside the daemon (which check keyed it —
  responsible-pid binding, client entitlement evaluation, or TCC.db
  policy for `kTCCServicePostEvent`) was not opened. If the intent is to
  make a *legitimate* input client pass, its identity/entitlement story
  is the next open question — answered by the daemon's own logs/code, not
  by transport work.
- The shared `get_bool("result")` parser breakpoint (0x1850d07b0) stayed
  0-hit because preflight's handler parses keys inline — expected, not a
  gap in the reply evidence (the `OS_xpc_dictionary` type + inline
  get_bool reads are the reply proof).
- `macws_runtime_diagnostics_enabled()` caches on first call, so
  `XPC_TRACE` cannot retroactively show the `->` arrow for a WS that
  started before the marker existed; functional proof supersedes it here.
- `EnablePressuredExit` is stock plist semantics — launchd may retire the
  daemon when idle; `start_tccd_system` re-arms it on each startup and
  verifies both pid and registered endpoint.
