## Changes requested — D114 is not approved as lifecycle-safe

Static review of `analysis/d113-trace-transport/d113_transport.c` found a
producer-admission gap: `d113_record()` checks `shutdown` before incrementing
`in_flight` (lines 109–115). A producer suspended between those operations
is invisible to `d113_quiesced()` (245–250). `d113_free()` can therefore
free the transport before that producer resumes. This was tested with a
temporary copy of the source containing a deterministic pause exactly
between those operations; the repository source was not edited. Exact run:

```text
clang -fsanitize=address -g -Ianalysis/d113-trace-transport \
  -o /tmp/macpad_d114_race_test /tmp/macpad_d114_race_test.c \
  /tmp/macpad_d114_race.c -lpthread
ASAN_OPTIONS=detect_leaks=0 /tmp/macpad_d114_race_test
```

Verbatim decisive output:

```text
paused-before-inflight quiesced=1 free=0
ERROR: AddressSanitizer: heap-use-after-free
WRITE of size 8 ... in d113_record macpad_d114_race.c:115
freed by thread T0 ... in d113_free macpad_d114_race.c:270
```

The temporary source inserted `test_pause_before_admission()` immediately
before the existing `in_flight` increment. This is a deterministic schedule
counterexample to the claimed ownership protocol, not a naturally observed
production crash. The independent frontend review and the repair packet will
make the required lifetime boundary explicit.

The same design question applies to `drain_active`, `d113_drain_final()`,
and `d113_free()`: their correctness needs an admission/owner contract that
prevents a new API entry after teardown begins. An atomic count alone cannot
protect a raw pointer from a caller that starts after it is freed. Document
that external lifetime boundary and make the in-object admission transition
atomic for already-started callers; add deterministic race tests for both
producer and drainer. Do not add a wait under the pacing lock.
