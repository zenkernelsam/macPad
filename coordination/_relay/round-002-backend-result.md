## 1. Private ABI audit (FACT, disassembly)

**SkyLight caller** (`analysis/SkyLight_22F82`, `_audit_token_check_tcc_access`):

```
185425df4  ldp q0, q1, [x20]        ; x20 = caller's 32-byte audit token pointer
185425df8  stp q0, q1, [sp]         ; copy token to outgoing stack slot
185425dfc  mov x1, sp               ; x1 = pointer to token copy
185425e00  mov x0, x19              ; x0 = CFString service (from arg x1)
185425e04  mov x2, #0               ; options = NULL
185425e08  blraaz x8                ; call TCCAccessPreflightWithAuditToken
185425e0c  cmp w0, #0
185425e10  cset w0, eq              ; allowed iff TCC result == 0
```

**TCC callee** (`analysis/TCC_22F82`, `0x1850d03bc`):

- `0x1850d03d8 mov x19, x0` (service).
- `0x1850d0420 stur x1, [x29, #-0x68]` — stores **x1 only**, i.e. a
  pointer to the token; later the code treats that slot as a value in the
  CFDictionary it builds and calls `TCCAccessRequest`.
- `0x1850d0528 mov x0, x19; 0x1850d052c retab` — return value is a
  **32-bit int in w0** (`ldr w19, [x8, #0x18]` at `0x1850d0500`).
- x2 (third argument) is overwritten inside the function; options are not
  consumed. SkyLight passes `x2=0`.

**Probe compiled call** (`_main`, deployed/staged probe):

```
100000a60  ldp q0, q1, [sp, #0x20]  ; 32-byte token copied from task_info slot
100000a64  stp q0, q1, [sp, #0x60]
100000a68  add x1, sp, #0x60        ; x1 = pointer to token copy
100000a6c  mov x2, #0              ; options = NULL
100000a70  blr x20                  ; dlsym-resolved TCCAccessPreflightWithAuditToken
```

**Conclusion:** the source typedef

```c
typedef int64_t (*PreflightAuditFn)(CFStringRef, audit_token_t, CFDictionaryRef);
```

does **not** literally describe the callee (it uses a pointer to the
token), but on arm64 AAPCS64 passes aggregates larger than 16 bytes
indirectly. The compiled probe therefore performs exactly the same copy
to stack + `x1 = pointer` + `x2 = NULL` sequence as SkyLight. The
`int64_t` return is benign because the callee writes `x0` via a 32-bit
`w19` load (`mov x0, x19` zero-extends). Service representation is a
CFString in the client and an XPC string in the request (server log:
`service="kTCCServicePostEvent"`). The probe's by-value typedef and
`int64_t` should still be tightened to `const audit_token_t *` and `int`
in the next source packet — they are correct by calling convention, not
by declaration.

**Static control flow that produces the empty dictionary** (tccd arm64e,
`/tmp` analysis copy matching sha256 above):

- Reply dictionary is created early: `0x100006500 mov x28,x0;
  0x100006508 bl _xpc_dictionary_create_reply; 0x10000650c mov x23,x0`.
- On a request/attribution failure the handler reaches `0x1000069ac`
  (request context nil), evaluates the logging gate at `0x1000069c8
  cbnz w0, 0x100007928`, otherwise falls to `0x1000069cc`.
- `0x100007928 bl 0x100052ca4` is the sole call site of the helper that
  logs `"Failed to create attribution chain from message."`
  (`0x100052cc0`), then `0x100007930 b 0x1000069cc`.
- `0x1000069cc..0x1000069e0` releases and sends **x23** unchanged:
  `mov x0,x28; mov x1,x23; bl _xpc_connection_send_message`.
  No `xpc_dictionary_set_*` runs on this path, so the client receives
  `count = 0`.

Therefore the accessor-zero seen in R007/R008 is a **pre-policy
attribution-chain failure**, not a TCC grant decision and not an
explicit `result=false`. The service was never evaluated.

## 3. Probe context vs WS sender (FACT + THEORY)

FACT from the same bounded A/B:

- uid 0 caller (`launchdchrootexec 0 0`) and uid 501 caller
  (`launchdchrootexec 501 501`), same 7-key schema, both receive
  `count = 0` and both log the responsibility/attribution failure. A
  simple uid switch is not the differentiator.
- `kTCCServicePostEvent`, `kTCCServiceSystemPolicyAllFiles` and
  `kTCCServiceAccessibility` all return the same empty dictionary.
- The probe's `ping` message (a different minimal dictionary, no
  `function`) also receives `count = 0`; that is a separate early path,
  but it confirms the reply default is an empty dictionary rather than a
  populated sorry/error object.
- A real WS-sender post (`macos_ws_event_probe postmin`,
  `SLSPostEventRecord -> rc=1002`) produced **0** tccd log lines in the
  oslog window: the live WS had a cached checker result and did not issue
  a fresh TCC request. No new WS request was forced because this round
  must not restart the owner's generation.

THEORY (not proven): the SSH/launchdchrootexec probe has no
responsibility policy for its audit token, so tccd cannot build the
attribution chain. A fresh WS generation started as
`UIKitApplication:com.macwsguide.windowserver` may have a valid
responsibility policy and may get a populated reply. If it instead also
logs `Policy not found`, then the chroot WS launch/attribution contract
is the common root cause of both empty replies and input denial, and the
fix belongs there, not in TCC grants or checker overrides.
